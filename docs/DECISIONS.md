# 判断の記録

一度決めたことを蒸し返さないための記録。
「何を決めたか」だけでなく「なぜ」と「何を捨てたか」を書く。

書き方:

```
## YYYY-MM-DD 見出し
**決めたこと**: …
**理由**: …
**捨てた案**: …
```

---

## 2026-09-xx テナント分離は共有DB＋club_id＋RLS
**決めたこと**: クラブごとにデータベースやスキーマを分けず、1つのテーブルを
`club_id` で分け、RLSで守る。
**理由**: 1人で運用するため、クラブが増えるたびにDBが増える構成は保守できない。
**捨てた案**: クラブごとに別DB／別スキーマ。

## 2026-09-xx LINEプロバイダーはクラブごとに作る（B案）　※2026-10-14 に取り消し（下の「Clubena共通のミニアプリ1つ」）
**決めたこと**: Clubena共通のプロバイダーではなく、クラブごとにプロバイダーを作り、
その配下にミニアプリチャネルとMessaging APIチャネルを置く。
**理由**: 同意画面にクラブ名が出て保護者に自然。userIdがクラブ内で閉じるため、
テナントをまたぐ名寄せが構造上起きない。委託先という法的な立て付けとも合う。
**捨てた案**: Clubena単一プロバイダー（A案）。管理は楽だが、同意画面の事業者名が
Clubenaになり、クラブ間でuserIdが共有される。

## 2026-10-xx 住所などはシステムに持たず、紙でクラブが保管する
**決めたこと**: システムが持つのは 氏名・ふりがな・生年月日・緊急連絡先・規約同意 の
5項目のみ。住所などは紙で集め、会員IDで紐付けてクラブが保管する。
ファイルアップロード機能は作らない（紙のスキャン保存を防ぐため）。
**理由**: 委託範囲が小さいほど、事故も契約も運用も軽くなる。
**捨てた案**: 住所も含めてシステムで持つ。

## 2026-10-09 1つのログインは1つのクラブにだけ属する
**決めたこと**: `profiles` の1行＝1人＝1クラブ。2つのクラブで働くコーチは、
クラブごとに別のログインになる。
**理由**: 権限の判定が「自分のクラブ」1つで済み、単純で間違えにくい。
LINEの連携（`line_identities`）も「クラブ＋LINEユーザーID」の組で持つので、
同じ保護者が2つのクラブに子を通わせていても、クラブごとに別のログインとして扱える。
**捨てた案**: 1人が複数クラブに所属できる形。判定が複雑になり、取り違えの余地が増える。

## 2026-10-09 クラブをまたいだ参照をデータベースが拒否する
**決めたこと**: 別のテーブルを指すときは、IDだけでなく「club_id とID」の組で指す。
**理由**: 伊丹の出欠がエースの会員を指す、といった取り違えを、画面のコードの
バグがあってもデータベースが受け付けない。RLSと二重の守りになる。
**捨てた案**: IDだけで指す（一般的だが、取り違えを防げない）。

## 2026-10-09 緊急連絡先は関数経由でのみ、記録付きで読み書きする
**決めたこと**: `member_private` には許可を1つも書かず、テーブルへの権限も取り上げる。
読み書きは `reveal_emergency_contacts` / `save_emergency_contacts` だけ。
呼ぶたびに `access_logs` に残る。読めるのは事務・保護者・担当コーチに加えて、
振替でその子が来る回の担当コーチ。
**理由**: 体育館での事故のとき、振替で来た子の連絡先を現場のコーチが確かめられる
必要がある。それ以外の担当外のコーチには見せない。

## 2026-10-09 フィードバックと引き継ぎメモは別のテーブル
**決めたこと**: `feedbacks`（保護者に見せる）と `handover_notes`（見せない）を分け、
引き継ぎメモには保護者向けの許可を一切書かない。
**理由**: 1つのテーブルを「公開する／しない」の印で分けると、印の付け間違いや
許可の書き間違い1つで内部のメモが保護者に見える。テーブルを分ければ構造上起きない。

## 2026-10-09 お知らせの宛先は、送った時点の会員を書き出しておく
**決めたこと**: 送信時に `notice_recipients` に宛先の会員を書き出し、
保護者はそこに自分の子がいるお知らせだけを見る。
**理由**: 宛先を毎回計算すると、後から入会した人に過去のお知らせが届いたり、
クラス替えで宛先が変わったりする。

## 2026-10-09 欠席の締切判定・級の履歴はデータベースが自動で行う
**決めたこと**: 欠席が締切内かは、出した瞬間にデータベースが判定し、後から書き換えられない。
「1つだけ」のタグを付け替えると、履歴が自動で残る（タグ名はその時点の文字で保存）。
**理由**: 画面の作りに関係なく必ず守られる。保護者が締切内に書き換える、
コーチの操作手順によって履歴が抜ける、といったことが起きない。

## 2026-10-09 未ログインの人には何も使わせない
**決めたこと**: anon（未ログイン）からは、すべてのテーブルと関数の権限を取り上げる。
**理由**: 入会申込もLINEでログインしてから行う設計なので、未ログインで使う画面がない。
8月の案にあった「未ログインで書き込める入会申込テーブル」は不要になった。

## 2026-10-14 LINEは「Clubena共通のミニアプリ1つ」。クラブごとの公式アカウントは作らない
**決めたこと**: Clubena のプロバイダーを1つ、LINEミニアプリのチャネルを1つだけ作り、
全クラブで共有する。どのクラブかはURLの後ろ（`/itami/` など）で分ける。
クラブ側では LINE Developers の作業も、公式アカウントの作成・Messaging API の設定もしない。
**理由**: クラブごとにプロバイダー・ミニアプリ・公式アカウントを作って管理する負担が、
運営（自分）にとってもクラブにとっても大きすぎる。さらに、公式アカウントが配信ツールの
プロバイダーに固定されている場合に、通知もリッチメニューも使えなくなる危険があった。
クラブの分離は、データベース（`club_id`＋RLS、`line_identities` のクラブ単位の登録）が担うので、
プロバイダーを分けなくても他クラブのデータは見えない。
**捨てた案**:
- クラブごとのプロバイダー（B案）。上の負担と危険のため
- LINEを使わない（メールの6桁コード、SMS）。保護者がふだん見ているのはLINEで、
  ログインはLINEで行いたいため
- ノーコードツール（Glide・Bubble・Softr・FlutterFlow）。人数課金でクラブが増えるほど赤字になる、
  LINEログインに標準で対応していない、データが米国に置かれる、作り済みのRLSとテストを捨てることになる
**引き受けること**:
- 保護者の同意画面に出る名前はクラブ名ではなく「Clubena」になる。
  プライバシーポリシー雛形と覚書に「委託先 Clubena を通じてLINEのユーザーIDを取得する」と書く
- IDトークンの aud（チャネルID）ではクラブを区別できない。`line-auth` は
  「URLのクラブに、そのLINEユーザーが登録されているか（`line_identities`）」でクラブをまたいだログインを防ぐ
- 1つのミニアプリで複数のクラブにサービスを出すことが、認証審査で認められるかは未確認。
  未認証のまま使う分には審査はない

## 2026-10-14 v1の通知は「アプリの中に出す」だけ。LINEへのプッシュはしない
**決めたこと**: 公式アカウントを持たないので、LINEのトークにメッセージは送らない。
開講日の確定・中止・振替の確定・お知らせ・未納のお知らせは、保護者のホーム画面の表示と未読バッジで知らせる。
クラブには、今使っているLINE（グループや既存の公式アカウント）で「アプリを確認してください」と
一言流してもらう運用にする（文例を用意する）。
**理由**: 公式アカウントの作成・管理・料金をなくすため。プッシュがどうしても必要になったら、
そのとき Clubena の公式アカウントを1つだけ作る（クラブごとには作らない）。
`message_log` テーブルはそのときのために残しておく。
**捨てた案**: メール通知（保護者が見ない・キャリアメールに届かない）、Webプッシュ（iPhoneはホーム画面に追加した人だけ）。

## 2026-10-14 導入作業は運営（自分）が代行する。Excelで受け取り、Excelで返せるようにする
**決めたこと**: クラス・料金プラン・タグ・名簿の初期設定は、クラブからExcelを受け取って自分が取り込む。
クラブの担当者には「確認してください」だけを頼む。運用が始まってからも、名簿・出欠・月謝は
Excelで書き出せるようにする。
**理由**: 導入でいちばん高い壁は、最初の設定作業。担当者が慣れている道具（Excel）との行き来を
1つの画面で済ませれば、「アプリに全部入れ直す」負担がなくなる。

## 2026-10-14 機能は段階的に開く（クラブ設定 `config.features`）
**決めたこと**: 最初の2週間は「予定・欠席・出席・お知らせ」だけを開き、慣れてから
月謝・振替・級・シフト・フィードバックを順に開く。開け閉めはクラブ設定の `features` で行い、
閉じている機能はメニューごと画面に出さない。切り替えは導入代行の一部として自分が行う。
**理由**: 最初から全機能を見せると、担当者も保護者も迷う。使う画面が少ないほど、最初の定着が早い。

## 2026-10-22 Excel取り込みは全クラブ共通の形1つ。チェックは1つのファイルにまとめる
**決めたこと**: ひな形はクラブごとに変えず、全クラブ同じ列・同じシート（はじめに・クラス・料金プラン・タグ・名簿）にする。
クラブごとの違いは中身（クラス名・料金の決め方・タグのグループ）で吸収する。列の定義は `public/js/import/schema.js`、
チェックは `public/js/import/rules.js` の1か所だけに書き、運営の手元の道具（`tools/import/`）とのちの事務画面（工程5-11）が同じものを使う。
あわせて次を決めた。
- 列は見出しの文字で探す（並べ替えても読める。見出しを変えると読めない）
- 会員番号は、今の番号を引き継ぎたいクラブだけ書く。空の人には「最大の番号の次」から振る
- 家族は「家族」の記号でまとめ、空なら緊急連絡先1の電話でまとめる。招待案内は家族ごとに1枚
- 「LINEを使わない」に「はい」の会員は、紙で規約に同意済みとして記録し、招待案内を出さない
- カタカナのふりがな、先頭の0が消えた電話番号、グループ名を省いたタグは自動で直し、直したことを青で知らせる
- 間違いが0件になるまで取り込まない。確認結果はExcelで出し、そのままクラブに返せる形にする
**理由**: 何クラブにも同時に提案・導入するには、クラブごとに形を作り分ける手間をなくす必要がある。
チェックを1か所にまとめれば、運営が手元で通したファイルは事務画面でも必ず通る。
**捨てた案**: クラブごとにひな形を作り分ける（数が増えると保守できない）／
Googleスプレッドシートで受け取る（クラブ側にGoogleアカウントが要る・共有設定で個人情報が漏れやすい）／
名簿だけ受け取り、クラス・料金は画面で設定する（担当者の最初の作業が増える）。

## 2026-10-22 画面の配信は Cloudflare Workers の静的配信にする（Pagesではなく）
**決めたこと**: Cloudflare 上の `clubena` は Workers として作られているので、そのまま Workers の静的配信を使う。
設定はリポジトリ直下の `wrangler.jsonc` に書き、`public/` をビルドなしで配信する。
どのURLでも index.html を返すのは `_redirects` ではなく `"not_found_handling": "single-page-application"` で行う。
**理由**: Workers では `_redirects` の `/* /index.html 200` が無限ループとして無視され、`/itami/` が 404 になる。
設定をリポジトリに置けば、ダッシュボードの設定に頼らず、手元（`npx wrangler dev`）と本番が同じ動きになる。
**捨てた案**: Pages のプロジェクトを作り直す（作り直すとURLが変わる。いまの Workers で困ることがない）／
`_redirects` を `/* / 200` にして続ける（動くが、規則の意味が読み取りにくく、ほかの規則と干渉しやすい）。

## 2026-10-22 新しく入会する人は、申込を始めた時点で「子のいない保護者」として登録する
**決めたこと**: 招待コードを持たない人が「はじめて入会を申し込む」を押すと、`line-auth` が
そのクラブの保護者として登録し（`profiles`・`line_identities`）、セッションを出す。
子（`guardian_members`）は申込が承認されるまでつながない。
**理由**: 入会申込もログインしてから行う設計（未ログインには何も使わせない）なので、
申込の前にセッションが要る。子がつながらない保護者には、RLSによりクラブのデータが何も見えないので、
誰でも登録できても漏れるものはない。DBを変えずに済む。
**捨てた案**: 承認するまで登録しない（B）。申込者のLINEユーザーIDを承認まで置いておくテーブルが要り、
マイグレーション（008）が増える。
**引き受けること**: 申込を送らないまま残る「子のいない保護者」の行ができうる。事務の画面で消せるようにする。

## 2026-10-24 入会申込は「保護者だけが呼べる関数」1つで受け、きょうだいの緊急連絡先は共通にする
**決めたこと**: 入会申込フォーム（工程4-5・4-6）の送信は `submit_application`（`010_application.sql`）1回で、
子（申込中）・保護者とのつながり・緊急連絡先・規約の同意をまとめて登録する。全部入るか、何も入らない。
あわせて次を決めた。
- 一緒に申し込むきょうだいには、同じ緊急連絡先を登録する（子ごとに変えたいときは、承認後に登録情報で直す）
- 規約は、クラブのいちばん新しい版にだけ同意できる。開いているあいだに改定されたら、規約の段からやり直してもらう
- 1回に5人まで、1人の保護者の申込中は10人まで。同じ保護者が同じ子（ふりがな＋生年月日）を2回は申し込めない
- 生年月日は年・月・日を選ぶ形にし、年には和暦を添える。学年・年齢は入力中に画面で計算して出す
  （計算は `public/js/grade.js`。SQL と同じ答えになることをテストで確かめる。保存した会員の学年は引き続き SQL の値を正とする）
**理由**: 保護者は `members` に直接書けない（007）ので、入口を1つの関数に絞れば権限と中身の確かめが1か所で済む。
途中で失敗して「子だけ入って同意がない」状態を作らないため、1つのトランザクションにした。
きょうだいの緊急連絡先は同じことが多く、入力の手間を減らすほうが、デジタルに不慣れな保護者には大事。
**捨てた案**: 子ごとに緊急連絡先を入れる（入力が人数分に増える）／
画面から members などに直接書けるよう RLS を広げる（保護者が書ける範囲が広がりすぎる）／
生年月日をスマホの日付の選択で入れる（数年前の日付までさかのぼる操作が大変）。

## 2026-10-24 規約の同意はホームの前で求め、緊急連絡先は押したときだけ読む
**決めたこと**: 登録情報と規約の再同意（工程4-9）で、次のようにした。
- クラブの会員規約のいちばん新しい版に、まだ同意していない子が1人でもいれば、ホームの前に同意の画面を出し、同意するまで進めない。
  改定のときは「会員規約が改定されました」、一度も同意していないとき（Excel で取り込んだ家庭が初めて開いたときなど）は
  「会員規約への同意のお願い」と出し分ける。同意は対象の子の全員分を1回で入れる
- 未同意かどうかは、ホームを開くときの読み込みに `terms_versions`・`terms_consents` を足して画面で突き合わせる（関数を作らない）
- 登録情報の緊急連絡先は、開いただけでは読まず、「表示する」を押したときだけ `reveal_emergency_contacts` で読む
- 緊急連絡先の変更は、きょうだいにも同じものを登録することを選べる（申込のときと同じ考え方）
- 名前・生年月日・クラスは保護者が変えられない。変えたいときはクラブに連絡してもらう
**理由**: SPEC の「改定すると、保護者は次にアプリを開いたとき再同意画面が出る」をそのまま満たし、同意のない利用を作らない。
007 の許可（保護者は自分の子の分を、アプリ・本人名義で、いちばん新しい版にだけ入れられる）で足りるので、DB を変えずに済む。
緊急連絡先を読む関数は呼ぶたびに記録が残るので、画面を開くたびに読むと、見ていない記録が増えて記録の意味が薄れる。
**捨てた案**: 同意をホームの上のお知らせにして、後回しにできるようにする（未同意のまま使い続けられてしまう）／
同意の有無を返す関数を作る（マイグレーションが増え、読み込みが1回増える）／登録情報を開いたら緊急連絡先も読む。
**引き受けること**: 取り込んだ家庭は、初めて開いたときに必ず同意の画面を通る（紙で同意済みの家庭は、事務担当が紙の同意を記録すれば出ない）。

## 2026-10-25 職員の画面は事務担当とコーチで1つの枠を使い、やることは呼んだ人の権限で数える
**決めたこと**: 職員の画面（工程5-1・5-2）で、次のようにした。
- 事務担当とコーチは同じ枠（上・左のメニュー・中身）を使い、メニューの項目を役割と開いている機能で出し分ける。
  メニューにない画面は URL を直接開いてもホームに戻す（保護者の画面と同じ考え方）
- ホームの「やること」は関数 `staff_todo()` を1回呼んで数える。security invoker（呼んだ人の権限）にして、
  事務担当にはクラブ全体、コーチには担当クラスの分だけが RLS で数えられるようにした。保護者が呼ぶとエラー
- 「出欠の未入力」は、確定・会場変更の、終わった回（過去31日）で、在籍中の子がいて、出欠の記録が1人分もない回とする。
  1人でも入っていれば入力したとみなす
**理由**: 役割ごとに別の画面を作ると、ログイン・メニュー・機能の開け閉めの処理が二重になる。
数える処理を画面で行うと、開講日と出欠を全部読むことになり、件数が増えると遅くなる。関数1つなら1回の往復で済む。
security definer にすると、コーチにも他のクラスの分が数えられてしまうおそれがあるため、権限は RLS に任せた。
31日は、月をまたいでも前の月の分が見える長さ。古すぎる回は「やること」から外す。
**捨てた案**: 事務担当とコーチで別の画面を作る／画面で開講日と出欠を読んで数える／
「出欠の未入力」を、在籍中の全員分がそろっていない回とする（欠席の子は記録しない運用だと、ずっと残り続ける）。

## 2026-10-25 会員番号はクラブの行で数え、紙の申込書からの登録は承認待ちを通らない
**決めたこと**: 入会承認と紙の申込書からの登録（工程5-4・5-5）で、次のようにした。
- 会員番号は `clubs.last_member_no` を1つ進めて決める。欠番は使い回さない。Excel の取り込みなどで、それより大きい番号が
  すでにあれば、その次から振る。番号の発行は関数（`approve_member`・`register_paper_member`）の中だけで行う
- 承認するとき、クラスも一緒に決める（在籍中の子は必ずクラスに入る決まりのため）。対象学年に合うクラスを先に選んでおく
- 紙の申込書からの登録は、承認待ちを通らずに、すぐ在籍中・番号の発行まで行う。同意は「紙」・入力した事務担当の名義で記録する
- 同じふりがな・生年月日の子は、紙の登録では止める。LINEの申込では止めずに、承認の画面で注意を出す
  （在籍中の家庭が招待コードを使わずに申し込んだ場合など、事務担当が確かめて決める）
- 申込は取り消せる（申込中の子を消す。つながり・緊急連絡先・同意も一緒に消える）
- 2つの関数は security invoker（呼んだ人の権限）。事務担当の権限は 007 の許可で足りる
**理由**: 番号を「いまある最大の番号＋1」で決めると、最後の会員を消したときに同じ番号が出て、紙の書類と食い違う。
クラブの行を更新して数えれば、同時に2人を承認しても重ならない。
紙の申込は事務担当が紙を見ながら入れるので、もう一度承認する手順はいらない。
LINEの申込は保護者が入れたものなので、同じ子かどうかの判断は人に任せる。
**捨てた案**: 番号を PostgreSQL のシーケンスで数える（クラブごとに作る必要があり、取り込みの番号と合わせにくい）／
紙の申込も申込中で入れて承認する（同じ人が2回操作することになる）／LINEの申込で同じ子を自動で止める（取り違えのとき保護者に理由を説明できない）。

## 2026-10-25 名簿の学年はビューで計算し、規約の改定は関数1つで版を上げる
**決めたこと**: 会員名簿と設定（工程5-6・5-8）で、次のようにした。
- 名簿はビュー `staff_roster` を読む。学年・年齢はビューの中で `grade_label`・`age_on` を使って出し、画面では計算し直さない。
  職員だけに出す（保護者が読んでも0行）。security_invoker なので、コーチには担当クラスの子だけになる
- 名簿の緊急連絡先は、行を開いて「表示する」を押したときだけ読む（記録が残る関数のため。登録情報と同じ）
- 名簿の絞り込み・並べ替え・探す処理は画面で行う（1クラブの会員は数百人までなので、全員を1回で読む）
- クラスは消さず、「使わない」にする。使わないクラスは承認・紙の登録で選べないが、今いる子はそのまま
- 規約の改定は関数 `publish_terms()` だけで行い、版を1つ上げる。公開する前に「保護者が同意し直す」ことを知らせ、
  もう一度押してもらう。いまの版と同じ本文は公開しない
**理由**: 仕様書 4-1-1 のとおり、学年はデータベースの関数を正とする（完了条件「学年が grade_label と一致」）。
規約の番号を画面で数えると、同時に2人が改定したときに番号がぶつかる。関数の中でクラブの行を押さえて数えれば重ならない。
公開は取り消せず、全家庭に再同意を求めることになるので、一度立ち止まる手順を入れた。
**捨てた案**: 学年を画面（grade.js）で計算する／名簿を1ページずつ読む（人数が少なく、探すたびに通信するほうが遅い）／
クラスを消せるようにする（前の開講日・出欠が指しているため消せない）。
